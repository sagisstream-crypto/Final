# Бэктест ALTSIG на истории Binance USDT-M (Node)

Годовой прогон сигнального движка ALTSIG (`index-6.html`) по настоящим
архивам Binance: **01.09.2025 — 31.08.2026**, 365 дней, только фьючерсы.

## Чем это отличается от `backtest-node/`

`backtest-node/` гоняет другое приложение — сканер выносов со SCORE/VEL1M/QUIET,
у которого движок бэктеста уже лежал внутри `index.html`. У ALTSIG такого
движка нет, поэтому `analyze()` пришлось портировать на исторические ряды:
формулы всех компонентов скопированы построчно, отличается только то, что
значения берутся по индексу бара, а не с хвоста массива.

## Источник данных

`api.binance.com` и `fapi.binance.com` отвечают **451 (гео-блок)**, поэтому всё
берётся с `data.binance.vision`:

| что | откуда |
|---|---|
| список пар | S3-листинг `monthly/klines/` (вместо `exchangeInfo`) |
| свечи 5m/15m/1h/4h | `monthly/klines/` |
| открытый интерес | `daily/metrics/` (шаг 5 минут, 365 файлов на пару) |
| фандинг | `monthly/fundingRate/` |
| базис перп/индекс | `monthly/premiumIndexKlines/` |

Список пар из архива, а не из `exchangeInfo`, заодно возвращает делистнутые
пары — выборка не смещена в сторону выживших.

## Что восстановлено, а что нет

Из 15 компонентов движка исторически доступны **13**:

* **нет `book` (перекос стакана, вес 8)** — `bookDepth` публикуется только
  посуточно и весит ~0,5 МБ на пару в день: 74 ГБ на год по вселенной;
* **нет `liq` (ликвидации, вес 6)** — `liquidationSnapshot` за этот период не
  публикуется (404).

Это 14 веса из 132. Шкала score не съезжает: в `analyze()` стоит
`score = num/den*100`, то есть нормализация по сумме весов присутствующих
компонентов, а не по полной.

Ещё отличия от live:
* `t.burst` (всплеск из сокета) недоступен — компонент `volume` считается
  только по z-счёту объёма;
* тикер недоступен, поэтому `fresh = false` и цена берётся как последнее
  закрытие 5m — то есть вход по закрытию бара, без заглядывания вперёд;
* индикаторы считаются по непрерывному ряду, а не по окну `limit=200`; для
  EMA9/21/50 и RSI14 разница исчезает после ~200 баров прогрева.

## Определение winrate

Взято из самого приложения (`openJournal`/`updateJournal`), не выдумано:

* стоп задет → **−1R**;
* TP2 (+2R) задет → **+2R**;
* иначе через 24 часа от входа → текущий R;
* если бар задел и стоп, и тейк — засчитывается стоп (в приложении `hitStop`
  проверяется первым);
* лимитный вход, не исполнившийся за 90 минут → `cancelled`, в winrate не
  входит, но пару всё это время блокирует.

Воспроизведены и оба ограничителя частоты: кулдаун 30 минут на пару
(`S.seen`) и запрет второй открытой записи по той же паре.

**Важно:** `winrate` = доля сделок с `result > 0`, а закрытие по 24-часовому
таймауту с результатом +0,01R тоже считается победой. Поэтому в отчётах рядом
печатается «чистый» winrate = TP2 / (TP2 + стопы), и на swing эти две цифры
расходятся втрое.

## Порядок запуска

```bash
node universe.mjs                                  # вселенная фьючерсов + суточные объёмы
NW=6 node --max-old-space-size=13000 run.mjs       # ~15 мин, 3 пресета, 23,2M строк
node --max-old-space-size=13000 report.mjs         # сетка порог × грейд × сторона × ATR
PRESET=intraday node --max-old-space-size=13000 report2.mjs   # фильтры + подбор весов
PRESET=intraday node --max-old-space-size=13000 report3.mjs   # перебор на обучении -> контроль
node --max-old-space-size=13000 report4.mjs        # сводная таблица
```

`run.mjs` держит в таблице только бары с `|score| >= 30` при заводских весах —
ниже этого ни один порог перебора (минимум 40) сигнала не даст, даже с запасом
на изменение весов.

## Размер выборки

* вселенная: **637 пар** (USDT-перпы минус `DEFAULT_EXCLUDE` и `JUNK_RE`,
  с объёмом ≥ $3M хотя бы 30 дней в году);
* строк в таблицах: scalp 17,1M · intraday 4,96M · swing 1,20M = **23,2M**;
* перебрано около **5 000** конфигураций (пресет × порог × грейд × сторона ×
  множитель стопа × фильтр BTC × согласные/против × объём × веса).

Обучение — сен'25–фев'26, контроль — мар'26–авг'26. Ни одна цифра из контроля
не участвовала в подборе.
