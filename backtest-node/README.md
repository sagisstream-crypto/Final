# Бэктест порогов сканера на исторических данных Binance (Node)

Прогон движка из `index.html` по настоящим минуткам фьючерсов Binance USDT-M
за 6 полных месяцев: **01.03.2026 — 31.08.2026**, 184 дня.

## Зачем отдельный слой данных

Блок `BT-DATA` в `index.html` ходит в `api.binance.com` / `fapi.binance.com`.
Из окружения, где это запускалось, оба хоста отвечают **451 (гео-блок)**.
`data.binance.vision` при этом доступен и закрывает обе потребности:

* список пар — S3-листинг `data/futures/um/monthly/klines/`
  (863 пары к USDT, **включая делистнутые** — это снимает survivorship bias,
  про который предупреждает комментарий в `BT-CORE`);
* суточные свечи для отбора вселенной — месячные архивы `1d`;
* минутки — месячные архивы `1m` (дешевле REST, как и просил постановщик).

## Что переиспользуется дословно

`extract_engine.mjs` вырезает из `index.html` по маркерам и складывает в `engine.mjs`:

* `computeScore` (секция `v15: composite score`),
* `BT-CORE-START … BT-CORE-END` — расчёт признаков и сбор событий с MFE/MAE,
* `BT-SWEEP-START … BT-SWEEP-END` — `btEval`, `btMarginal`, `btOptimize`, Уилсон.

Правил сигналов никто не переписывал. Единственная правка — `BT_MAX_EVENTS`
становится читаемым из env: 300 000 рассчитаны на телефон, здесь таблица живёт
в 13 ГБ heap.

Доп. фильтры, которых нет в конфиге движка (потолки по тейкер-доле и среднему
чеку), сделаны не правкой `btEval`, а подтаблицей: фильтры в `btEval`
применяются до проверки кулдауна, поэтому отсев строк заранее даёт ровно тот же
результат.

## Порядок запуска

```bash
node list_syms.mjs        # symbols_all.json — все пары из S3-листинга
node fetch_daily.mjs      # daily.json — суточные свечи (~6 МБ)
node universe.mjs         # universe.json — кто проходил фильтр шапки и в какие дни
node extract_engine.mjs   # engine.mjs — блоки из index.html
NW=4 node --max-old-space-size=12000 run_all.mjs   # ~25 мин, таблица событий
node --max-old-space-size=12000 report.mjs   # сетка score × Δ1м, срезы, baseline
node --max-old-space-size=12000 report2.mjs  # координатный поиск, обучение/контроль
node --max-old-space-size=13000 report3.mjs  # фильтры-потолки, лестница
node --max-old-space-size=13000 report4.mjs  # чувствительность к каждому порогу
```

`run_all.mjs` качает архивы во временный кэш по одной паре и удаляет сразу после
разбора, поэтому пикового диска нужно мегабайты, а не гигабайты. Результат —
`table_cols.bin` (~2,7 ГБ) и `table_meta.json`; в репозиторий они не кладутся.

## Отбор и размер выборки

Отбор как в приложении: цена < $10 и объём 24ч ≤ $5M **на момент сигнала** —
поминутно, по скользящему 24-часовому окну, а не по суточной свече.

* вселенная: 519 пар, 60 753 пара-дня;
* просканировано 526 пар × 184 дня;
* 68 млн минут-кандидатов → **12 227 367 событий** в таблице.

На входе в таблицу отсеиваются минуты, недостижимые ни одним порогом сетки
(`d1m ≥ $5k` или `d2m ≥ $5k` или `score ≥ 40` или сработала тихая полка).
Проверено отдельно: на сетке порогов это не теряет ни одного события QUIET и ни
одного SIGNAL при любом score ≥ 50.

## Оговорки, которые остаются

1. Минутные свечи: порог 10с (SPIKE) на них не виден, сверху он ограничен
   строкой VEL1M с тем же значением.
2. Стакана и спреда в истории нет — в `computeScore` они дают от −10 до +10,
   поэтому backtest-score примерно на 5 пунктов ниже живого.
3. Тейкер-доля в бэктесте есть по всем парам, в live — только по 12 горячим.
4. MFE — это лучшая цена, которой рынок касался внутри окна, а не результат
   сделки: реальный выход всегда хуже. Рядом с каждой цифрой выноса напечатан
   MAE, чтобы было видно просадку до движения.
