# Тихая полка → вынос: методика исследования

Наработанный пайплайн и, что важнее, список ловушек, каждая из которых
однажды уже дала неверный ответ в этом проекте.

## Данные

Binance REST геоблокирует часть регионов (HTTP 451). Рабочий источник —
официальный архив, он открыт отовсюду:

```
https://data.binance.vision/data/futures/um/monthly/klines/{SYM}/{TF}/{SYM}-{TF}-{YYYY-MM}.zip
https://data.binance.vision/data/futures/um/daily/klines/{SYM}/{TF}/{SYM}-{TF}-{YYYY-MM-DD}.zip
```

Список пар — через S3-листинг (сам `data.binance.vision/?prefix=…` отдаёт HTML):

```
https://s3-ap-northeast-1.amazonaws.com/data.binance.vision?delimiter=/&prefix=data/futures/um/monthly/klines/&max-keys=1000
```

Объёмы: год 15m по 864 парам ≈ 830 МБ parquet, качается за ~40 минут в 64 потока.
Год 1m по всем парам — 13+ ГБ, обычно не нужен: берите стратифицированную
панель из 150–200 пар.

Текущего месяца в monthly нет — добирайте daily-файлами.

## Пять ловушек

### 1. Сырой процент движения = замаскированная волатильность

Любой отбор по «цена сходила на +5%» находит волатильные монеты, а не сетап.
Самые красивые сырые проценты дают **широкие** полки, то есть уже разогнанные
инструменты.

Лечение — одно из двух:
- **матчинг по децилям волатильности** при сравнении сетапов;
- **нормированная цель**: `fmax / ATR_полки >= K` вместо `fmax >= X%`.

Проверка, что вы попались: если у обученной модели главный вес — ATR со знаком
плюс, она детектор волатильности, а не сетапа.

### 2. 15-минутные OHLC не знают, что было раньше — тейк или стоп

Любой бэктест с TP и SL на OHLC без внутрибарного пути завышает результат.
Берите минутные свечи и проходите путь: первое касание вверх против первого
касания вниз. При совпадении в одной минуте считайте стопом.

### 3. Целевая метрика — не «поймать первый бар»

Только 36% выносов детектируются на первом баре импульса, 100% — в пределах
восьми. Правильная метрика recall: **сигнал в окне [начало, начало+8],
после которого до пика осталось ещё ≥5% хода**. Иначе вы либо занижаете
recall втрое, либо засчитываете входы на самом пике.

### 4. Шлюз и ранжирование нужно разделять

Одна модель на весь рынок вырождается в детектор волатильности. Работает
двухступенчатая схема: жёсткий шлюз фиксирует паттерн, модель ранжирует
**внутри** шлюза. Пороги шлюза подбирайте перебором по критерию «сколько
реальных событий поймано при бюджете N алертов в сутки», а не на глаз.

### 5. Интуитивные признаки часто не работают

Проверяйте, не предполагайте. В этом проекте:
- доля тейкер-покупок — **вес ≈ 0**, хотя кажется главной;
- «слишком тихая полка» — ловушка: порог ATR 0.6% выбрасывает 88% выносов;
- «не гнаться за ценой» — вредно: ограничение пробоя 2% вместо 25% теряет
  две трети выносов без выигрыша в качестве;
- узкая полка по **ширине** — плохое определение, правильное через **ATR**.

## Что оказалось предсказательным

| признак | знак | смысл |
|---|---|---|
| размах бара / ATR полки | + | сильнейший; расширение диапазона, а не объём |
| рост за 3 бара / ATR | + | импульс копится |
| рост за 1 бар / ATR | − | одиночная вертикальная свеча хуже разгона |
| объём против суточной базы | − | сутки не должны быть уже разогреты |
| ускорение объёма за бар | − | накопление лучше выброса |
| позиция в 30-дневном диапазоне | − | низ лучше вершины |
| движение BTC за 1.5ч | − | выносы альтов идут в паузах BTC |
| доля тейкер-покупок | ≈0 | не работает |

## Диапазоны, найденные на годе данных

- **Оборот 24ч:** максимум частоты 10–100 млн $, максимум абсолютного числа
  3–10 млн. Рабочая полоса сканера 1 млн – 300 млн: сужение до «оптимума»
  стоит половины пойманных событий.
- **ATR полки:** ≤1.8% на 15m бар, насыщение — жёстче только теряете.
- **Окно полки:** 48 баров 15m = 12 часов.
- **Потолок погони:** +25% к потолку полки.
- **Час суток:** 12–15 UTC — больше всего алертов при худшем качестве.

## Порт модели в JS-сканер

Обязательно кросс-проверяйте покомпонентно: экспортируйте из Python
сырые бары + посчитанные признаки + score для 5–10 случаев, считайте то же
в Node и сравнивайте относительные расхождения. Целевая точность — 1e-6.
Типичные расхождения: порядок окна (`shift(1)` или нет), медиана против
среднего, включён ли текущий бар в ATR, `fillna` до или после нормировки.
